DOMUS API ENDPOINTS - CONTRATO COMPLETO DE LA API

Flutter usage notes
- Este archivo es la fuente de verdad de rutas, permisos, body y JSON de respuesta de toda la API.
- La base de todas las rutas es `/api`.
- Todos los cuerpos y respuestas son JSON salvo que se indique lo contrario.
- Los IDs son `integer`; las fechas/horas son `string` ISO-8601 salvo que se indique `YYYY-MM-DD`.
- Una respuesta de error siempre tiene al menos `{ "message": "string" }`.
- Una validacion Laravel puede agregar `errors: { "campo": ["string"] }` y responde `422`.
- Un token inexistente o invalido responde `401`; un rol o recurso sin permiso responde `403`; un recurso no encontrado responde `404`.
- No convertir un campo ausente en `0`: primero verificar la ruta exacta documentada.
- Use .agents/flutter_app_docs/00_general_flutter_plan.txt as architecture base.
- Then pass one screen TXT from .agents/flutter_app_docs per Flutter task.
- Parent and child/member screens should be separate pages/providers, not one giant role-conditional page.
- After POST actions, update UI with the returned entity/balance first, then refresh the list if needed.
- If an action returns unlocked_badges, show a badge earned modal/toast.
- Cobertura: este archivo refleja las 56 combinaciones metodo/ruta definidas en `routes/api.php`. Las rutas web de Blade/admin no son endpoints de esta API y no se mezclan aqui.

Convencion monetaria
- Los campos `*_cents` son enteros en centavos de MXN. Ejemplo: `10000` = `$100.00`.
- Los campos `*_display` son textos ya formateados, por ejemplo `"$100.00"`.
- Algunos modulos reciben dinero como `string` en el body, por ejemplo `"20.50"`.
- Prestamos y tareas tienen campos principales en pesos enteros: `loan.amount: 100` y `task.reward_amount: 100` significan `$100.00`; no dividirlos entre 100.
- En cada endpoint se especifica si un nombre ambiguo como `remaining_balance` representa centavos o pesos.

Allowances
`AllowanceBase` = `{ id: integer, parent_user_id: integer, child_user_id: integer, amount_cents: integer, next_payment_amount_cents: integer|null, frequency: daily|weekly|monthly|ten_seconds, start_at: string, next_run_at: string|null, first_payment_immediate: boolean, status: pending|active|paused, last_executed_at: string|null, last_failed_at: string|null, created_at: string, updated_at: string, child: UserChild, parent: UserParent }`.
`amount_cents` is the permanent amount. `next_payment_amount_cents`, when non-null, is the one-time override for the next successful payment and is cleared after that payment. The current API writes only `pending`, `active` and `paused` to `status`.
`AllowancePayment` = `{ id: integer, allowance_id: integer, scheduled_for: string, status: string, amount_cents: integer, parent_balance_before: integer|null, parent_balance_after: integer|null, child_balance_before: integer|null, child_balance_after: integer|null, executed_at: string|null, failed_at: string|null, failure_reason: string|null, created_at: string, updated_at: string }`.

GET /api/allowances
Auth: parent
Success `200`:
```json
{
  "allowances": ["AllowanceListItem"],
  "summary": {
    "pending_due_payments": "integer",
    "pending_due_payments_capped": "boolean",
    "allowances_with_pending_due_payments": "integer",
    "paused_due_allowances": "integer"
  }
}
```
`AllowanceListItem` = `AllowanceBase` plus `{ due_payments_count: integer, due_payments_count_capped: boolean, has_due_payments: boolean, latest_payment: AllowancePayment|null }`.
The four extra fields above are present only because this endpoint calculates the due-payment preview and loads `latestPayment`. `pending_due_payments` counts due payment periods only for non-paused allowances. `allowances_with_pending_due_payments` counts non-paused allowances with at least one due period. `paused_due_allowances` counts paused allowances with at least one due period, not the number of their due payments.

POST /api/allowances
Auth: parent
Body: child_user_id, amount, frequency, first_payment_immediate, start_at
Body types: `child_user_id:integer`, `amount:string` normal money format, `frequency:daily|weekly|monthly|ten_seconds`, `first_payment_immediate:boolean`, `start_at:date` required when immediate is false.
The selected user must belong to the authenticated parent's family or the endpoint returns `422`. When `first_payment_immediate:true`, a supplied `start_at` is ignored; `start_at` is set to today and `next_run_at` to the current second.
Success `201`:
```json
{ "message": "string", "allowance": "AllowanceBase", "result": "AllowanceExecutionPaid|null" }
```
When `first_payment_immediate:true`, the allowance is paid immediately and `result` is an `AllowanceExecutionPaid`. When false, `result:null` and the saved allowance remains `pending` until execution. The returned `allowance` loads `child` and `parent`; it does not include `latest_payment` or the three calculated `due_*` fields.

PATCH /api/allowances/{allowance}
Auth: parent
Path `allowance`: integer allowance ID owned by the parent.
Body: amount, one_time optional, paused optional
Body types: `amount:string` in normal money format (`20`, `20.5`, `20.50` or with a decimal comma), with up to two decimals; `one_time:boolean` defaults to `false`; `paused:boolean`.
Success `200`:
```json
{
  "message": "string",
  "one_time": "boolean",
  "paused": "boolean",
  "next_payment_date": "string|null",
  "next_payment_amount_cents": "integer",
  "next_payment_amount_display": "string",
  "allowance": "AllowanceBase"
}
```
`amount` is required for a quantity change, and `one_time:true` also requires `amount`. `one_time:true` applies that amount only to the next successful payment. With `one_time:false` or when omitted, `amount_cents` changes permanently and any pending one-time override is removed. Existing `AllowancePayment` records are never changed. `amount` and `paused` may be sent together.
To pause or resume without changing the amount, send only `{ "paused": true }` or `{ "paused": false }`. A paused allowance keeps its amount, pending one-time override and `next_run_at`; the scheduler and manual execution do not pay it while paused. Because `next_run_at` is not advanced, overdue periods remain due and are processed after resuming.
The top-level `one_time` reports whether an override remains saved after the update. The top-level `next_payment_amount_cents` and `next_payment_amount_display` are the effective next amount: they use the override when present and otherwise the permanent amount. The nested `allowance.next_payment_amount_cents` remains the raw nullable override. The returned `allowance` does not include `latest_payment` or the calculated `due_*` fields.

POST /api/allowances/{allowance}/execute
Auth: parent
Path `allowance`: integer allowance ID owned by the parent.
This endpoint executes with `force:true`: except for a paused allowance, it ignores `start_at` and whether `next_run_at` is still in the future. It pays the period identified by the current `next_run_at` and then advances the schedule.

New successful payment, `200` (`already_executed` and `advanced_schedule` are absent):
```json
{
  "executed": true,
  "message": "string",
  "remaining_parent_balance": "integer (centavos comprometidos/usados)",
  "remaining_parent_balance_display": "string",
  "child_balance_cents": "integer",
  "child_balance_display": "string",
  "allowance": "AllowanceBase",
  "payment": "AllowancePayment"
}
```
`AllowanceExecutionPaid` is the response shape above. A successful payment uses `next_payment_amount_cents` when present, otherwise `amount_cents`; afterward it clears the one-time override and advances `next_run_at`.

If a paid `AllowancePayment` already exists for the current `allowance_id` and `next_run_at`, the same response fields are returned, `child_balance_cents` and `child_balance_display` may be null, and these two additional keys are present:
```json
{ "already_executed": true, "advanced_schedule": true }
```
No money is moved again; the allowance schedule is advanced.

Paused allowance, `200` (all payment and balance keys are absent):
```json
{ "executed": false, "message": "Esta mesada esta pausada.", "allowance": "AllowanceBase" }
```
The returned `allowance` in every execution variant loads `child` and `parent`; it does not include `latest_payment` or the calculated `due_*` fields.

Savings boxes
GET /api/savings-boxes
Auth: family user
Success `200`: `{ "savings_boxes": ["SavingsBox"] }`.
For parent, each box includes `members: User[]` and `accounts: SavingsBoxAccount[]` for all members.
For child/member, only active boxes where the user has an account are returned; each box includes `parent: UserParent` and the authenticated user's account(s).
`SavingsBox` = `{ id: integer, parent_user_id: integer, name: string, duration_months: integer|null, duration_days: integer|null, cycle_days: integer|null, cycle_count: integer|null, plan_version: string|null, max_per_cycle_cents: integer|null, max_amount_cents: integer|null, starts_at: string|null, cutoff_at: string|null, delivery_date: string, benefit_percent: string|null (decimal with 2 places), benefit_mode: final_balance_simple|legacy_accrual|null, annual_gain_percent: string (compatibility field), allow_early_withdrawal: boolean, audience: all|specific, status: active|completed|string, settled_at: string|null, accepts_deposits: boolean, created_at: string, updated_at: string, parent: UserParent|null, members: User[], accounts: SavingsBoxAccount[] }`.
For new boxes, the plan is frozen when it is created. `duration_months`, `duration_days`, `cycle_days`, `cycle_count`, `plan_version`, `max_per_cycle_cents`, `max_amount_cents`, `starts_at`, `cutoff_at`, `benefit_percent` and `benefit_mode` must be read from the saved box; never recalculate an existing plan from current configuration. `delivery_date` and `annual_gain_percent` remain populated for compatibility, but `cutoff_at` and `benefit_percent` are the authoritative fields for new boxes.
`max_per_cycle_cents` applies independently to each member account and each fixed-day cycle. `max_amount_cents` is derived as `max_per_cycle_cents * cycle_count` and limits the principal currently held by that member account. The final partial cycle receives the complete per-cycle allowance.
`SavingsBoxAccount` = `{ id: integer, savings_box_id: integer, user_id: integer, principal_cents: integer, principal_pending_cents: integer, earned_interest_cents: integer, settled_principal_cents: integer, settled_benefit_cents: integer, settled_total_cents: integer, interest_remainder_microcents: integer, last_interest_accrued_on: string|null, interest_accrued_until_at: string|null, settled_at: string|null, current_cycle_number: integer|null, deposited_in_current_cycle_cents: integer|null, remaining_in_current_cycle_cents: integer|null, remaining_total_capacity_cents: integer|null, created_at: string, updated_at: string, user: UserChild|null }`.
The cycle usage fields are runtime values added by the GET response for new-plan accounts. Settlement fields remain zero/null until the final payout.

GET /api/savings-boxes/creation-options
Auth: parent
Success `200`: `{ "creation_options": { "plan_version": "fixed_days_ceil_v1", "is_preview": true, "preview_starts_at": "ISO-8601 datetime", "cycle_days": integer, "cycle_label": string, "months_available": integer[], "duration_options": [{ "duration_months": integer, "label": string, "duration_days_preview": integer, "cycle_count_preview": integer, "max_total_multiplier_preview": integer, "cutoff_at_preview": "ISO-8601 datetime" }] } }`.
Use this read-only endpoint to initialize the new-box form before a box exists. `cycle_days` is the current configured cycle length (for example `14`) and `cycle_label` is ready to display (for example `Cada 14 días`). Each duration option previews how many cycles that calendar duration would produce if created at `preview_starts_at`. `max_total_multiplier_preview` equals the preview cycle count, so the client may preview `max_per_cycle * max_total_multiplier_preview`.
The endpoint creates no database records. Preview dates and counts can change if the box is created later; the authoritative values are always those returned and persisted by `POST /api/savings-boxes`.

POST /api/savings-boxes
Auth: parent
Body: name, duration_months, max_per_cycle, benefit_percent, allow_early_withdrawal, audience, member_user_ids[]
Body types: `name:string`, `duration_months:integer` included in the current `savings_box.months_available` configuration (default `[1,2,3]`), `max_per_cycle:string` normal money format and greater than zero, `benefit_percent:number` 0..1000, `allow_early_withdrawal:boolean`, `audience:all|specific`, `member_user_ids:integer[]` required and non-empty for `specific`.
Success `201`: `{ "message": "string", "savings_box": "SavingsBox" }`.
The client does not send a start date, cutoff date, cycle count or total maximum. At creation, the API reads the current configured `days_per_cycle` (default `14`), sets `starts_at`, calculates `cutoff_at` by adding the selected calendar months without overflow, rounds the real duration up to complete cycles, derives `max_amount_cents`, and persists every value as an immutable plan snapshot. Later configuration changes affect only newly created boxes.

The box must be active, `cutoff_at` must still be in the future, and the member must have an account. Money is moved manually from the member's available balance into `principal_cents`; new-plan boxes do not accrue time-based interest.
For new boxes, `cycle_number` is calculated from the saved `starts_at` and `cycle_days`. Gross deposits made in the same cycle cannot exceed `max_per_cycle_cents`; withdrawals do not restore already-used cycle allowance. A cycle-limit violation returns `422` with `cycle_number`, `remaining_cycle_cents` and `remaining_cycle_display`. The current principal also cannot exceed the derived `max_amount_cents`; a total-limit violation returns `422` with `max_amount_cents`, `current_amount_cents`, `remaining_capacity_cents` and `remaining_capacity_display`. Limits are independent for each member account.

POST /api/savings-boxes/{savingsBox}/withdraw
Auth: child/member
Body: amount
Success `200`: the deposit response shape except `deposited_in_cycle_cents` is not returned; it includes `cycle_number`, `remaining_cycle_cents`, `remaining_cycle_display`, `max_amount_cents`, `current_amount_cents`, `remaining_capacity_cents` and `remaining_capacity_display` after the withdrawal.
The box must be active, before `cutoff_at`, allow early withdrawal, and the authenticated account's principal must cover the amount. A withdrawal returns principal to the member's available balance and frees total principal capacity, but it does not restore the gross-deposit allowance already used in the current cycle. For new boxes, no benefit is paid on withdrawal; the final benefit is calculated only from the principal that remains at cutoff.

Automatic settlement (no HTTP endpoint)
At the configured daily time (default `23:59`), the scheduler calls `SavingsBoxSettlementService::runDue()`. The service selects active boxes whose frozen `cutoff_at` has arrived. For every member account it calculates `settled_benefit_cents = round(principal_cents * benefit_percent / 100)`, credits principal plus benefit to the member's available balance, records balance and savings-box movements, fills the settlement fields, clears held principal, and marks the box `completed` with `settled_at`.
Settlement is transactional and idempotent: calling the service again does not pay a completed box twice. At or after `cutoff_at`, manual deposits and withdrawals are blocked while the box waits for the scheduler. Parent GET responses continue to include completed boxes and their settlement history; child/member GET responses only include active boxes.

Loans

Contrato de importes - obligatorio
- Los campos monetarios directos del objeto `loan` son pesos mexicanos, no centavos:
  `amount`, `total_amount`, `installment_amount` y `fixed_interest_amount` son `integer`.
  Ejemplo: `amount: 100` significa `$100.00 MXN`; no dividir entre 100.
- El objeto `loan` NO devuelve `amount_cents`, `total_amount_cents` ni `installment_amount_cents` en la raiz.
- Los campos monetarios de pagos, `payment_summary`, `installment_plan` y saldos que terminan en `_cents` son centavos (`integer`).
- Los campos que terminan en `_display` son textos listos para mostrar, por ejemplo `"$100.00"`.
- `remaining_balance` en las respuestas de crear oferta y aprobar es un saldo usado/comprometido en centavos (`integer`), aunque el nombre diga "remaining". Su texto equivalente es `remaining_balance_display`.

Diagnostico del caso que muestra `$0.00`
- La ruta correcta del importe solicitado es `response.loans[i].amount` en los GET, o `response.loan.amount` en los POST.
- Para un prestamo de $100, la API debe entregar `loan.amount: 100`, `loan.total_amount: 100` o el total calculado, nunca `0`.
- No leer `loan.amount_cents`, `loan.total_amount_cents`, `loan.data.amount` ni `loan.payment_summary.amount`: esas rutas no existen para el importe principal y un valor ausente no debe convertirse silenciosamente en cero.
- La web confirma el contrato actual porque renderiza `loan.amount` y `loan.total_amount` directamente.
