DOMUS API ENDPOINTS - CONTRATO COMPLETO DE LA API

Flutter usage notes
- Este archivo es la fuente de verdad de rutas, permisos, body y JSON de respuesta de toda la API.
- La base de todas las rutas es `/api`.
- Todos los cuerpos y respuestas son JSON salvo que se indique lo contrario.
- Los IDs son `integer`; las fechas/horas son `string` ISO-8601 salvo que se indique `YYYY-MM-DD`.
- Una respuesta de error siempre tiene al menos `{ "message": "string" }`.
- Una validacion Laravel puede agregar `errors: { "campo": ["string"] }` y responde `422`.
- Un token inexistente o invalido responde `401`; un rol o recurso sin permiso responde `403`; un recurso no encontrado responde `404`.
- No convertir un campo ausente en `0`: primero verificar la ruta exacta documentada.
- Use .agents/flutter_app_docs/00_general_flutter_plan.txt as architecture base.
- Then pass one screen TXT from .agents/flutter_app_docs per Flutter task.
- Parent and child/member screens should be separate pages/providers, not one giant role-conditional page.
- After POST actions, update UI with the returned entity/balance first, then refresh the list if needed.
- If an action returns unlocked_badges, show a badge earned modal/toast.
- Cobertura: este archivo refleja las 61 combinaciones metodo/ruta de `routes/api.php` y `routes/billing_demo.php` (incluido desde el primero). Las rutas web de Blade/admin no son endpoints de esta API y no se mezclan aqui.
- Para campos de entrada con regla Laravel `integer`, se aceptan enteros JSON y cadenas que `FILTER_VALIDATE_INT` reconozca como enteros; `boolean` admite booleanos JSON, `0`, `1`, `"0"` y `"1"`; `numeric` admite números JSON y cadenas numéricas. Las reglas `string`, `regex`, `in`, `min` y `max` de cada endpoint restringen además estos conjuntos. Los tipos declarados de salida se refieren al JSON serializado, no al tipo del campo de entrada.

Acceso a funciones: regla global para toda la API
- El backend centraliza la decision en `User::isEnabledFunctions(): bool`. El front recibe un booleano JSON real, nunca `"true"`/`"false"` ni `0`/`1`. Puede formatear fechas y ordenar la informacion para mostrarla, pero no calcula vencimientos ni decide si una suscripcion da acceso.
- Una cuenta `parent` tiene acceso mientras siga vigente su periodo gratuito O tenga Premium real vigente. Por defecto el periodo termina exactamente en `created_at + 15 dias`; `FREE_TRIAL_DAYS` configura `access.trial_days`. El superadmin puede fijar otro vencimiento por cuenta sin cambiar `created_at`. Al llegar a la fecha exacta de vencimiento, ese periodo ya no da acceso.
- Los roles `child` y `member` comparten el acceso del `parent` asociado en `family_members`; crear un integrante no inicia otro periodo gratuito. Sin padre asociado, el acceso a funciones es `false`.
- Premium se decide con la ultima verificacion guardada para el producto configurado: `verified_at` descendente y, si empata, `id` descendente. Requiere `acknowledged = true`, vencimiento futuro y estado `SUBSCRIPTION_STATE_ACTIVE`, `SUBSCRIPTION_STATE_IN_GRACE_PERIOD` o `SUBSCRIPTION_STATE_CANCELED`. Una cancelacion conserva el acceso hasta acabar el periodo pagado. Una compra simulada (`DEMO_CONFIRMED`) no otorga Premium real.
- Se bloquean las 54 rutas de funciones, tanto consultas GET como escrituras: notificaciones, niveles/puntos, metas, saldo, retiros, transferencias, familia, mesadas, cajas de ahorro, prestamos, educacion y tareas. Los permisos de rol y pertenencia de cada seccion siguen aplicando cuando hay acceso.
- Estas siete rutas quedan disponibles aunque las funciones esten bloqueadas: `POST /api/register`, `POST /api/login`, `GET /api/me`, `GET /api/user`, `POST /api/logout`, `GET /api/billing/demo` y `POST /api/billing/demo/verify`. Las rutas privadas siguen requiriendo token; las de billing tambien requieren estar habilitadas en configuracion.
- Si una ruta de funciones devuelve el bloqueo de acceso, responde HTTP `403` con este JSON y no ejecuta la accion ni modifica sus datos:
```json
{
  "message": "Tu periodo gratuito ha terminado. Necesitas Premium para usar las funciones de Domus.",
  "code": "FUNCTIONS_DISABLED",
  "is_enabled_functions": false
}
```
- `code = FUNCTIONS_DISABLED` identifica esta alerta sin comparar el texto de `message`. Un `403` por rol/pertenencia no lleva este codigo ni implica que la suscripcion haya vencido. Un `401` sigue siendo un problema de autenticacion.
- Integracion Flutter: leer `user.is_enabled_functions` en registro, login y `GET /api/me`; en `GET /api/user` leer `is_enabled_functions` en la raiz. Si es `false`, bloquear las funciones y mostrar la alerta de acceso; conservar la sesion para consultar/comprar Premium o cerrar sesion. Para hijos/integrantes, el titular de su familia debe recuperar el acceso.
- Solo `GET /api/me` agrega `user.premium_expires_at: string ISO-8601 UTC|null`, con el ultimo vencimiento conocido de una compra real de la cuenta/familia, incluso si ya paso. Sin compra real con fecha conocida devuelve `null`. Es informacion para presentar en el front; no sustituye `is_enabled_functions` ni representa el vencimiento de la prueba gratuita.
- Comprobar el estado HTTP antes de interpretar el usuario: las respuestas de error de login/registro o `/me` no incluyen necesariamente `user` ni sus campos. El error `403` con `code: FUNCTIONS_DISABLED` tiene su propia forma, con la bandera en la raiz.
- Si una peticion falla con `403` y `code = FUNCTIONS_DISABLED`, actualizar el estado local a `false` y mostrar `message`. Esto cubre el vencimiento mientras la app sigue abierta. Tras consultar/verificar una compra, usar `data.is_enabled_functions` y refrescar `GET /api/me` cuando sea necesario. No sustituir esta bandera por `data.subscribed`: durante la prueba puede haber acceso sin compra.
- La bandera solo se incluye en las respuestas de autenticacion/usuario y billing indicadas, y en el error de bloqueo. No se agrega a cada respuesta funcional ni a los usuarios anidados de familia, tareas o prestamos. `trial_ends_at` y la relacion `current_subscription` no se exponen en el usuario autenticado.
- Esta regla global se aplica a todas las secciones funcionales siguientes aunque cada endpoint enumere solamente sus permisos y errores particulares. Las tareas programadas internas no son endpoints y conservan su ejecucion.

Convencion monetaria
- Los campos `*_cents` son enteros en centavos de MXN. Ejemplo: `10000` = `$100.00`.
- Los campos `*_display` son textos ya formateados, por ejemplo `"$100.00"`.
- Algunos modulos reciben dinero como `string` en el body, por ejemplo `"20.50"`.
- Donde se indica "formato monetario normal" para un `string` de entrada, la validacion usa `^\d+(?:[.,]\d{1,2})?$`: dígitos sin signo ni separador de miles, seguidos opcionalmente de `.` o `,` y uno o dos decimales. Cada endpoint determina por separado si acepta cero.
- Los importes principales del prestamo (`loan.amount`, `loan.total_amount`, `loan.installment_amount`, `loan.fixed_interest_amount` y sus snapshots) se serializan como cadenas decimales MXN con dos posiciones, por ejemplo `"100.00"` = `$100.00`; no dividirlos entre 100. `task.reward_amount` conserva su contrato propio de pesos enteros.
- En cada endpoint se especifica si un nombre ambiguo como `remaining_balance` representa centavos o pesos.

Auth
POST /api/register
Auth: none
Body: name, email, password, password_confirmation, terms_accepted
Body types: `name:string` requerido (max 255), `email:string` requerido (formato email, max 255, unico), `password:string` requerido (min 8), `password_confirmation:string` requerido e igual a password, `terms_accepted` requerido por la regla Laravel `accepted` (acepta `yes`, `on`, `1`, `true` o booleano `true`).
Success `201`:
```json
{
  "message": "Cuenta de padre creada correctamente.",
  "token": "<Sanctum token>",
  "user": {
    "id": 123,
    "name": "Ana",
    "email": "ana@example.test",
    "is_enabled_functions": true
  }
}
```
Tipos de salida: `message:string`, `token:string`, `user.id:integer`, `user.name:string`, `user.email:string`, `user.is_enabled_functions:boolean`.
La cuenta creada tiene rol `parent` y saldo inicial cero. Esta respuesta no incluye `user.role` ni `user.premium_expires_at`; consultar `GET /api/me` para obtener el usuario completo con esos campos.
`user.is_enabled_functions` refleja la regla global; normalmente es `true` al registrarse con la configuracion predeterminada de 15 dias. El cliente no puede modificar la bandera ni el vencimiento enviandolos en el body.

POST /api/login
Auth: none
Body: login, password
Body types: `login:string` requerido (email o username, max 255), `password:string` requerido.
Success `200`:
```json
{
  "message": "Inicio de sesión exitoso.",
  "token": "<Sanctum token>",
  "user": {
    "id": 123,
    "name": "Ana",
    "email": "ana@example.test",
    "username": null,
    "role": "parent",
    "is_enabled_functions": true
  }
}
```
Tipos de salida: `message:string`, `token:string`, `user.id:integer`, `user.name:string`, `user.email:string|null`, `user.username:string|null`, `user.role:parent|child|member`, `user.is_enabled_functions:boolean`.
No incluye `user.premium_expires_at`; despues de guardar el token, consultar `GET /api/me` para obtener esa fecha y el usuario completo.
Invalid credentials: `401 { "message": "string" }`.
Con credenciales validas el login sigue respondiendo `200` y entregando token aunque `user.is_enabled_functions` sea `false`.

GET /api/me
Auth: bearer token
Success `200`:
```json
{ "user": "MeUser", "parent_admin_name": "string|null", "is_family_member": "boolean" }
```
`user.is_enabled_functions` siempre esta presente como booleano y se calcula en el servidor con el acceso actual de la cuenta/familia. Un acceso vencido no impide consultar este endpoint: devuelve `200` y la bandera `false`.
`user.premium_expires_at` siempre esta presente en este endpoint como fecha/hora ISO-8601 UTC o `null`. Devuelve el ultimo vencimiento conocido de una compra real guardada para el producto configurado, ordenada por `verified_at` descendente y luego `id` descendente; ignora compras simuladas y registros sin fecha. Sin compra real con vencimiento conocido devuelve `null`, incluso durante la prueba gratuita. Conserva fechas pasadas cuando Premium ya vencio o no se renovo; cancelar tampoco borra la fecha. Para hijos/integrantes corresponde a la suscripcion del titular de su familia; sin titular devuelve `null`.
La fecha es informativa para mostrar/ordenar en el front; `user.is_enabled_functions` sigue siendo la decision de acceso. Se lee de los datos guardados, sin consultar Google Play. Este campo se agrega solo en `GET /api/me`, no en login, registro ni `GET /api/user`.
Ejemplos parciales de los campos de acceso dentro de `user` (los demas campos de `MeUser` tambien se devuelven):
```json
{ "user": { "is_enabled_functions": true, "premium_expires_at": null } }
```
El ejemplo anterior representa una cuenta durante su prueba gratuita sin compra real registrada. Si Premium vencio y tampoco queda prueba gratuita, ambos campos pueden ser:
```json
{ "user": { "is_enabled_functions": false, "premium_expires_at": "2026-10-20T12:00:00+00:00" } }
```
Un `premium_expires_at` no nulo no garantiza acceso actual: puede ser una fecha pasada o corresponder a una compra cuyo estado ya no da acceso. Las compras simuladas `DEMO_CONFIRMED`, otros productos y registros sin vencimiento no reemplazan la ultima fecha real conocida.
For a child/member, `user` includes the loaded `balance:BalanceRecord|null` relation; for a parent that relation key is absent. The appended `balance_cents` and `balance_display` are always part of the serialized user. `balance.amount` comes from an Eloquent model without a cast, so use `balance_cents` for a JSON integer with a guaranteed type.

GET /api/user
Auth: bearer token
Success `200`: serialized `User` object directly (not wrapped in `{user:...}`).
Incluye `is_enabled_functions:boolean` en la raiz. Este endpoint tambien sigue disponible con acceso vencido.
No agrega `premium_expires_at`; usar `GET /api/me` y leer `user.premium_expires_at` para obtener el ultimo vencimiento conocido de Premium.

POST /api/logout
Auth: bearer token
Success `200`: `{ "message": "string" }`. The current Sanctum token is revoked.
`config/sanctum.php` sets token `expiration` to `null`, and login/register create tokens without an individual expiration. There is no refresh-token endpoint. A `401` after authentication means the token is missing, invalid or revoked, or the server configuration has changed.

Billing / suscripciones Google Play
Contrato comun:
- Las dos rutas requieren `Authorization: Bearer <Sanctum token>` y comparten limite de 30 peticiones por minuto (`429` al excederlo). No exigen funciones habilitadas: una cuenta vencida debe poder recuperar su acceso.
- Si `billing_demo.enabled` es `false` (`GOOGLE_PLAY_DEMO_ENABLED=false`), responden `404`.
- `account_id` es un identificador opaco de la cuenta autenticada para asociar la compra de Google Play (`obfuscatedExternalAccountId`). No es el UUID `user.billing_account_id` y no deben intercambiarse.
- El registro usado por `isEnabledFunctions()` es el estado guardado de la compra; `GET /api/me` no consulta Google Play. Las rutas de billing consultan/verifican Google cuando estan en modo real. Aun no hay endpoint de webhooks.
- Ambas respuestas de exito usan la misma forma:
```json
{
  "data": {
    "account_id": "<identificador opaco de la cuenta>",
    "subscribed": true,
    "is_enabled_functions": true,
    "product_id": "domus_dummy",
    "expires_at": "2026-11-20T12:00:00+00:00"
  }
}
```
- Tipos de salida dentro de `data`: `account_id:string`, `subscribed:boolean`, `is_enabled_functions:boolean`, `product_id:string`, `expires_at:string ISO-8601 UTC|null`.
- `subscribed` indica si la compra consultada/verificada es elegible, esta reconocida y no ha vencido. `is_enabled_functions` es la decision final de acceso de la cuenta/familia, incluida la prueba gratuita. `expires_at` es el vencimiento de la compra devuelta para el usuario autenticado, no el de la prueba gratuita.
- `data.expires_at` de billing y `user.premium_expires_at` de `/me` son campos distintos. Billing puede devolver `expires_at:null` si Google ya no encuentra la compra, mientras `/me` conserva el ultimo vencimiento real conocido que siga guardado. Billing tambien puede devolver la fecha de una simulacion; `/me` la ignora. Para hijos/integrantes, `/me` usa la compra del titular de la familia, mientras billing consulta la compra del propio usuario autenticado.
- Con `GOOGLE_PLAY_DEMO_DUMMY_VERIFICATION=true`, una simulacion puede devolver `subscribed:true` pero no otorga Premium real; despues de la prueba gratuita `is_enabled_functions` puede seguir siendo `false`.

GET /api/billing/demo
Auth: bearer token (no requiere funciones habilitadas).
Body: ninguno.
Success `200`: forma comun de billing descrita arriba.
- Selecciona la ultima compra guardada del producto configurado para el usuario autenticado. En modo real consulta Google Play y actualiza su estado guardado, reconocimiento, vencimiento y fecha de verificacion.
- Sin compra guardada devuelve `subscribed:false` y `expires_at:null`, pero calcula normalmente `is_enabled_functions` (puede ser `true` durante la prueba).
- Si Google informa que la compra ya no existe/vencio, guarda el estado expirado y responde `subscribed:false`, `expires_at:null` y la bandera de acceso recalculada.
- Errors: `401` token invalido; `403` compra asociada a otra cuenta; `404` billing deshabilitado; `422` producto de compra incorrecto; `429` limite de peticiones; `503` fallo de configuracion/conexion/verificacion con Google Play. Los errores de billing no usan `FUNCTIONS_DISABLED`.

POST /api/billing/demo/verify
Auth: bearer token (no requiere funciones habilitadas).
Body: `product_id:string` requerido, debe coincidir con `config('billing_demo.product_id')` (actualmente `domus_dummy`); `purchase_token:string` requerido, maximo 4096 caracteres.
Success `200`: forma comun de billing descrita arriba.
- En modo real verifica la compra, el producto y que `obfuscatedExternalAccountId` coincida con la cuenta autenticada. Guarda la compra, y si es elegible pero aun no esta reconocida, completa su reconocimiento con Google Play.
- Una compra vigente verificada permite recuperar acceso inmediatamente: la respuesta recalcula `data.is_enabled_functions` tras guardarla. Un integrante sigue dependiendo de la suscripcion/prueba del padre, no de una compra propia.
- Un token de compra ya guardado para otra cuenta responde `403`. Repetir una verificacion de la misma cuenta actualiza su registro, sin crear otra suscripcion por el mismo token.
- Errors: `401` token invalido; `403` compra de otra cuenta; `404` billing deshabilitado; `422` body invalido, comprobante inexistente/vencido, producto incorrecto o compra pendiente; `429` limite de peticiones; `503` fallo de configuracion/conexion/verificacion/reconocimiento con Google Play. Una compra con estado no elegible puede devolver `200` con `subscribed:false`; no interpretar el HTTP `200` como Premium activo.

Automatic settlement (no HTTP endpoint)
At the configured daily time (default `23:59`), the scheduler calls `SavingsBoxSettlementService::runDue()`. The service selects active boxes whose frozen `cutoff_at` has arrived. For every member account it calculates `settled_benefit_cents = round(principal_cents * benefit_percent / 100)`, credits principal plus benefit to the member's available balance, records balance and savings-box movements, fills the settlement fields, clears held principal, and marks the box `completed` with `settled_at`.
Settlement is transactional and idempotent: calling the service again does not pay a completed box twice. At or after `cutoff_at`, manual deposits and withdrawals are blocked while the box waits for the scheduler. Parent GET responses continue to include completed boxes and their settlement history; child/member GET responses only include active boxes.

Loans

Contrato comun de prestamos
- Todas las rutas de esta seccion requieren `Authorization: Bearer <Sanctum token>` y estan bajo `auth:sanctum`. La identidad y el rol se obtienen del usuario autenticado, nunca de un `user_id` enviado en el body.
- Roles admitidos: `parent`, `child` y `member`. `child` y `member` usan las acciones del hijo. El padre solo puede actuar sobre prestamos cuyo `parent_user_id` sea su propio ID; el hijo solo sobre prestamos cuyo `child_user_id` sea su propio ID.
- Los importes de la raiz `loan` son cadenas decimales MXN de dos posiciones. Ejemplo: `"1800.50"` significa `$1,800.50`; no son centavos ni enteros. Los valores `*_cents` son enteros en centavos; `*_display` son cadenas formateadas.
- La API acepta importes numéricos con 0 a 2 decimales y máximo `999999999999.99`; el monto debe ser mayor que cero. Puede enviarse como número JSON o cadena numérica decimal. La base de datos los persiste con escala de 2.
- En préstamos, el decimal de entrada usa solo punto (`^\d+(?:\.\d{1,2})?$`); la coma aceptada por otros módulos no pasa la validación de estas rutas. No se admiten signos ni separadores de miles.
- Las fechas de columnas `date` del objeto `loan` se serializan por Laravel como strings de fecha/fecha-hora; `PaymentSummaryItem.due_date` y los pagos serializados dentro de `payment_summary` usan `YYYY-MM-DD`. Los timestamps son ISO-8601.
- No existe estado `cancelled`: los estados persistidos son `pending`, `offered`, `approved`, `rejected` y `paid`.
- Todos los movimientos de desembolso, crédito, reserva, liberación y cuotas son simulados en MXN y se aplican en transacciones. La reserva y el desembolso no se duplican al repetir acciones compatibles con idempotencia. El calendario solo se crea al desembolsar al hijo.
- El interés porcentual conserva la fórmula actual: `annual_interest_rate` se aplica una sola vez al principal, sin multiplicar ni prorratear por meses. Las cuotas distribuyen centavos enteros; cualquier residuo de la división se asigna a las primeras cuotas.

- No hay expiracion automatica de solicitudes ni ofertas. Mientras `status = offered`, el tiempo de espera no aumenta `total_amount`, no genera interes adicional y no crea cuotas; el interes se calcula una sola vez al guardar las condiciones.
- Estas operaciones no validan un saldo disponible ni un tope del padre. `remaining_balance` es el contador simulado de dinero usado/comprometido en centavos; una reserva aumenta el contador y un reembolso lo reduce. No representa dinero real disponible.
- Al pagar una cuota, el campo de respuesta `parent_balance_cents` informa el saldo simulado almacenado tras recibir ese pago. No es equivalente al `balance_cents` de la relacion `parent`, que para un padre es el contador de uso.

POST /api/loans
Auth: parent, child o member. La forma del body y la acción dependen del rol autenticado, como se describe a continuación.

Entrada inicial del hijo
- `POST /api/loans` distingue el flujo por `role` autenticado. Para `child` o `member`, el body admite exactamente `amount`, `reason` y `months`. Cualquier otra clave, incluida `child_user_id`, devuelve `422`.
- `amount`: requerido; numérico, > 0, máximo 2 decimales y máximo `999999999999.99`.
- `reason`: requerido; string de máximo 120 caracteres; no puede quedar vacío al recortarlo; rechaza etiquetas HTML (cuando `strip_tags` altera el texto) y caracteres de control. Se guarda recortado. Las comillas y otros caracteres ordinarios se guardan como texto y no se ejecutan como SQL.
- `months`: requerido; entero dentro de la lista permitida exacta `1`, `3`, `6`, `12`. Los meses representan cuotas mensuales.
- Validación adicional: el total debe alcanzar al menos un centavo por cuota; si `amount` en centavos es menor que `months`, responde `422`.
- El padre asociado se deriva de la relación familiar de la cuenta autenticada. Si no existe, el control global de acceso bloquea la peticion con `403`, `code: FUNCTIONS_DISABLED` e `is_enabled_functions:false`.
- Condiciones calculadas y guardadas por servidor: `installments_count = months`, `installment_frequency = monthly`, `has_interest = false`, `interest_mode = percent`, `annual_interest_rate = 0`, `fixed_interest_amount = "0.00"`, `total_amount = amount`, y `installment_amount` se calcula en centavos como el importe por cuota redondeado hacia arriba. `due_date` e `initial_due_date` se calculan a un mes calendario desde la fecha de solicitud, sin desbordar el último día del mes.
- Se guardan los tres datos originales en `requested_amount`, `requested_reason`, `requested_months`, además de las condiciones iniciales derivadas `initial_*`. No se crea una fila `loan_payments` ni se acredita saldo al enviar esta solicitud. Estado inicial: `pending`.
- Éxito `201`: `{ "message": string, "loan": Loan }`. No se serializa necesariamente la relación `payments` en esta respuesta de creación; `payment_summary` existe y tiene cero cuotas.
- Repetir este `POST` crea otra solicitud: no acepta clave de idempotencia.

Oferta iniciada por el padre
- `POST /api/loans` conserva el endpoint y sus campos. Para `parent`, el body validado es:

```text
child_user_id: integer, requerido; debe existir como users.id y pertenecer a la familia del padre con rol child o member
amount: número o string numérica decimal, requerido; > 0; 0–2 decimales; máximo 999999999999.99
reason: string|null, opcional; máximo 120 caracteres
due_date: fecha requerida, hoy o fecha futura
installments_count: integer requerido, entre 1 y 120
installment_frequency: weekly | biweekly | monthly, requerido
has_interest: boolean requerido
interest_mode: percent | fixed, requerido
annual_interest_rate: número requerido, entre 0 y 100, máximo 2 decimales
fixed_interest_amount: número/string decimal requerido, entre 0 y 999999999999.99, máximo 2 decimales
```

- Todos los campos indicados son requeridos salvo `reason`. Para ausencia de interés, el padre debe enviar `has_interest: false`, `annual_interest_rate: 0` y `fixed_interest_amount: 0`; la API normaliza `interest_mode` a `percent`. Con interés porcentual: tasa > 0 y monto fijo = 0. Con interés fijo: monto fijo > 0 y tasa = 0. Las combinaciones incoherentes devuelven `422` con mensaje y `errors.interest_mode`.
- El total calculado no puede superar `999999999999.99` ni ser menor que el número de cuotas en centavos; si no puede producir cuotas de al menos un centavo, devuelve `422`.
- Las claves no reconocidas no forman parte del contrato validado y se ignoran en esta ruta; no reemplazan valores validados.
- Se crea una oferta `offered`, con `requested_by_user_id` igual al padre y sin snapshots `requested_*` / `initial_*` del flujo del hijo. Se registra una reserva simulada del principal en el contador de dinero usado del padre. No se acredita al hijo ni se crea el calendario hasta que el hijo acepte.
- Éxito `201`: `{ "message": string, "loan": Loan, "remaining_balance": integer, "remaining_balance_display": string }`. Aquí `remaining_balance` es el total simulado usado/comprometido por el padre en centavos, pese al nombre; incluye la nueva reserva.

Relaciones serializadas por endpoint:
- `GET /api/loans` y `GET /api/loans/waiting`: `child` para parent; `parent` para child/member; siempre cargan `payments`.
- `POST /api/loans`: carga `child`; no serializa la relacion `payments`.
- `POST /api/loans/{loan}/approve`, `/review`, `/reject` y `/respond`: cargan `parent`, `child` y `payments`.
- `POST /api/loan-payments/{loanPayment}/pay`: `loan` carga `parent`, `child` y `payments`; el objeto raiz `payment` no carga una relacion `loan`.
GET /api/loans
Auth: parent, child o member.
Filtro: el padre recibe préstamos con su `parent_user_id`; el hijo/miembro recibe préstamos con su `child_user_id`.
Éxito `200`: `{ "loans": Loan[] }`. Incluye `payments`; incluye `child` para el padre e `parent` para hijo/miembro. `payment_summary` e `installment_plan` siguen las reglas anteriores.

GET /api/loans/waiting
Auth: parent, child o member.
Filtro del padre: préstamos propios en estado `pending`. Filtro de hijo/miembro: préstamos propios en estado `pending` o `offered`.
Éxito `200`: `{ "loans": Loan[] }`, con las mismas relaciones cargadas que `GET /api/loans`. En solicitudes/propuestas aún no desembolsadas, `payments` es `[]`.

- No existe un GET individual por ID: el hijo obtiene la propuesta desde `GET /api/loans/waiting` o `GET /api/loans`.
- Mientras `status = offered`, `due_date` en la respuesta es el vencimiento efectivo proyectado si el hijo acepta en ese momento; `proposed_due_date` conserva la fecha enviada por el padre.

POST /api/loans/{loan}/approve
Auth: parent propietario de la solicitud `pending` del hijo.
Body: vacío. Cualquier campo enviado devuelve `422`; para proponer condiciones distintas debe usarse `/review`.
Acción: aprueba exactamente las condiciones iniciales; en una transacción registra el débito simulado del padre, acredita el principal al hijo, marca `approved` y crea el calendario de cuotas. El primer vencimiento es un mes calendario después de la fecha de aprobación.
Éxito `200`: `{ "message": string, "loan": Loan, "remaining_balance": integer (centavos simulados usados/comprometidos por el padre), "remaining_balance_display": string, "child_balance_cents": integer, "child_balance_display": string }`.
Reintento: si el mismo préstamo ya está `approved`/`paid` y `funds_disbursed_at` existe, devuelve el estado financiero actual sin volver a acreditar ni recrear cuotas. Otro estado devuelve `422`; préstamo ajeno devuelve `403`.

POST /api/loans/{loan}/review
Auth: parent propietario de la solicitud del hijo.
Body: conjunto completo requerido de condiciones finales; no acepta claves adicionales:

```text
amount: número/string decimal MXN, > 0, 0–2 decimales, máximo 999999999999.99
due_date: fecha requerida, hoy o futura
installments_count: integer requerido, 1–120
installment_frequency: weekly | biweekly | monthly, requerido
has_interest: boolean requerido
interest_mode: percent | fixed, requerido
annual_interest_rate: número requerido, 0–100, máximo 2 decimales
fixed_interest_amount: número/string decimal requerido, 0–2 decimales, 0–999999999999.99
```

Las reglas de coherencia de interés y máximo del total son las mismas que en la oferta iniciada por el padre.
- Si el préstamo sigue `pending` y todas las condiciones coinciden con la solicitud tal como está (incluida la fecha inicial), se acepta directamente: desembolsa y genera el calendario en ese momento; respuesta de aprobación `200` como `/approve`.
- Si las condiciones difieren, se guardan como condiciones actuales completas, se preserva `requested_*`/`initial_*`, se escribe `proposed_due_date` y `parent_reviewed_at`, el estado pasa a `offered` y se reserva el principal simulado. No se acredita al hijo ni se crean cuotas aún. El hijo confirma o rechaza en `/respond`.
- Si cambia solo interés/plazo/frecuencia pero conserva la fecha inicial, el vencimiento efectivo se calcula desde la aceptación del hijo según frecuencia (7 días, 14 días o un mes calendario). Si el padre propuso otra fecha, la espera transcurrida desde la revisión se suma a esa fecha cuando se prepara el desembolso.
- Éxito `200` al proponer: `{ "message": string, "loan": Loan, "remaining_balance": integer (centavos usados/comprometidos), "remaining_balance_display": string }`. La relación `payments` se incluye como arreglo vacío. Repetir los mismos términos para una propuesta ya `offered` devuelve la propuesta existente sin otra reserva. Repetirlos después de desembolsar devuelve la respuesta de aprobación sin duplicar movimientos.
- Solo admite solicitudes `pending`, salvo los reintentos idénticos descritos. Otro estado o condiciones no idénticas en un reintento devuelven `422`; préstamo ajeno devuelve `403`.

POST /api/loans/{loan}/reject
Auth: parent propietario de solicitud del hijo en estado `pending`.
Body: `{ "reason": string|null }`; `reason` es opcional/null, máximo 255 caracteres. Claves distintas de `reason` devuelven `422`.
Acción: cambia estado a `rejected`, registra `parent_reviewed_at`, `responded_at` y el motivo recortado. Al rechazar una solicitud `pending` no hay reserva, transferencia, cambio de saldos ni reembolso.
Éxito `200`: `{ "message": string, "loan": Loan }`.
Reintento: si ya está `rejected` sin reserva, devuelve éxito sin repetir efectos. Otros estados devuelven `422`; préstamo ajeno devuelve `403`.

POST /api/loans/{loan}/respond
Auth: child o member propietario del préstamo `offered`.
Body exacto, sin claves adicionales:

```text
action: "accept" | "reject", requerido
reason: string|null, opcional, máximo 255 caracteres; para reject debe quedar no vacío después de recortar
```

`accept`: confirma íntegramente las condiciones guardadas, sin posibilidad de cambiarlas. En una transacción valida la reserva, acredita el principal al hijo, actualiza `due_date`/`funds_disbursed_at`/`responded_at`, cambia a `approved` y crea todas las cuotas. Primera cuota: fecha efectiva acordada según la regla de `/review`; el reloj de pago no empieza antes de la confirmación/desembolso.
`reject`: cambia a `rejected`, guarda motivo y `responded_at`, y libera la reserva del padre una sola vez. No acredita dinero al hijo ni crea cuotas.
Éxito `200` para ambas acciones: `{ "message": string, "loan": Loan, "member_balance_cents": integer, "member_balance_display": string, "remaining_balance": integer (centavos simulados usados/comprometidos por el padre), "remaining_balance_display": string }`.
Reintento: aceptar un préstamo ya `approved`/`paid` con desembolso registrado, o repetir rechazo de uno `rejected` con `funds_released_at`, devuelve el estado sin duplicar el abono, calendario o reembolso. Un estado distinto de `offered` devuelve `422`; préstamo ajeno devuelve `403`.

POST /api/loan-payments/{loanPayment}/pay
Auth: child o member propietario del préstamo activo `approved`.
Body: no se requieren campos; el endpoint no lee el body.
Condiciones: la cuota debe estar vencida hoy o antes, no estar pagada y el saldo del hijo debe cubrirla. En una transacción debita el saldo del hijo, acredita la cuenta simulada del padre, marca la cuota como pagada y actualiza el estado agregado del préstamo. No produce movimientos duplicados: el reintento de una cuota ya pagada responde `422`.
Éxito `200`:

```text
{
  message: string,
  payment: LoanPayment,
  loan: Loan,
  member_balance_cents: integer,
  member_balance_display: string,
  new_balance_cents: integer (alias de member_balance_cents),
  new_balance_display: string (alias de member_balance_display),
  parent_balance_cents: integer (saldo simulado almacenado tras recibir el pago; no es el contador de uso del padre),
  parent_balance_display: string,
  unlocked_badges: [{ id: integer, slug: string, title: string, description: string|null, text: string, image_url: string|null, points_reward: integer }],
  domus_points: { points: { historical: integer, earned: integer, spent: integer, available: integer }, level: DomusLevel|null }
}
```

Errores comunes de las rutas de préstamos
- `401`: token ausente/inválido o contexto autenticado ausente.
- `403`: acceso a funciones bloqueado (`code: FUNCTIONS_DISABLED`, `is_enabled_functions:false`), rol no autorizado o el préstamo/cuota no pertenece al usuario autenticado. Solo el bloqueo de acceso incluye ese codigo y bandera.
- `404`: ID de `loan` o `loanPayment` inexistente (route model binding).
- `422`: validación fallida, campo adicional prohibido en cuerpos estrictos, estado incompatible, reserva inconsistente, fecha aún no vencida o saldo insuficiente. La respuesta de validación Laravel usa `{ "message": string, "errors": { "campo": [string] } }`; algunos errores de estado devuelven solo `message`.

POST /api/education/lessons/{lesson}/complete
Auth: bearer token
Path `lesson`: integer lesson ID in an active course/category.
Success `200`:
```json
{
  "message": "string",
  "lesson_completion": { "lesson_id": "integer", "is_completed": "boolean", "completed_at": "string" },
  "progress": { "completed_lessons": "integer", "total_lessons": "integer" }
}
```

POST /api/education/lesson-parts/{lessonPart}/submit
Auth: bearer token
Path `lessonPart`: integer part ID in an active course/category. Only `quiz` and `exam` accept answers.
Body: `answers:array` con al menos un `{ question_uuid:string (max 100), answer:a|b|c|d }`.
Success `200`:
```json
{
  "message": "string",
  "assessment_uuid": "string",
  "assessment_type": "quiz|exam",
  "score": "integer",
  "total_questions": "integer",
  "percentage": "number",
  "saved": "boolean",
  "last_result": "AssessmentResult|null",
  "reward": "ExamReward|null",
  "achievements": [ { "title": "string", "text": "string", "points_reward": "integer" } ],
  "domus_points": "DomusPoints|null"
}
```
For an exam, at least 50% course progress is required; a failed progress gate returns `400` with `required_progress_percentage` and `current_progress_percentage`. Exam results are saved; quiz results are not saved.

Tasks
GET /api/parent/tasks
Auth: parent
Success `200`:
```json
{ "tasks": ["TaskParentListItem"], "available_balance_cents": "integer (centavos comprometidos/usados)", "available_balance_display": "string" }
```
`Task` = `{ id: integer, parent_user_id: integer, accepted_by_user_id: integer|null, completed_by_user_id: integer|null, member_completion_requested_at: string|null, name: string, description: string|null, reward_amount: integer (pesos MXN), reward_points: integer, status: open|accepted|in_progress|awaiting_parent_confirmation|completed|closed|ended|canceled, created_at: string, updated_at: string }`.
`TaskParentListItem` = `Task` más `{ accepted_by: TaskActor|null, completed_by: TaskActor|null }`. Solo `GET /api/parent/tasks` carga esas dos relaciones; los demás endpoints de tareas devuelven `Task` sin esas claves, salvo que la respuesta indique expresamente lo contrario.

POST /api/parent/tasks
Auth: parent
Body: name, description, reward_amount, reward_points
Body types: `name:string` requerido (max 120), `description:string|null` opcional (max 255), `reward_amount:integer` requerido en pesos MXN (min `0`), `reward_points:integer` requerido (`0..100`).
Success `201`: `{ "message": "string", "task": "Task", "available_balance_cents": "integer", "available_balance_display": "string" }`.

POST /api/parent/tasks/{task}/review
Auth: parent
Body: action approve/retry/cancel
Path `task`: integer task ID owned by the parent. Body `action:approve|retry|cancel`.
Success `200`:
```json
{
  "message": "string",
  "task": "Task",
  "available_balance_cents": "integer|null",
  "available_balance_display": "string|null",
  "available_child_balance_cents": "integer|null",
  "available_child_balance_display": "string|null",
  "unlocked_badges": ["Badge"],
  "domus_points": "DomusPoints|null"
}
```
`approve` pays the reward and fills child balance, badge and points. `retry` returns the task to `accepted` and all balance/badge/points fields are null/empty. `cancel` refunds the parent's reserved amount and returns parent balance fields.

GET /api/child/tasks
Auth: child/member
Success `200`:
```json
{ "tasks": { "open": ["Task"], "accepted": ["Task"], "ended": ["Task"] } }
```
`open` contains parent tasks with status `open`; `accepted` contains the authenticated child's accepted/in-progress/awaiting tasks; `ended` contains the child's completed/closed/ended/canceled tasks.

POST /api/child/tasks/{task}/accept
Auth: child/member
Path `task`: integer task ID in the child's parent context.
Success `200`: `{ "message": "string", "task": "Task" }`; status becomes `accepted`.

POST /api/tasks/member/completed/{task}
Auth: child/member
Path `task`: integer task ID accepted by the authenticated child/member.
Success `200`: `{ "message": "string", "task": "Task", "unlocked_badges": ["Badge"] }`; status becomes `awaiting_parent_confirmation`. No badge is unlocked at this stage.
